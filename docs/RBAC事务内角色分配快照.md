# 事务内角色分配快照

`RbacAuthorizeService.checkRoleAssignmentWithSnapshot` 用于可信服务端在同一数据库事务中新建目标组织、随后分配角色的场景。方法先调用可覆盖的原角色分配检查，再以快照重复检查角色授权和数据范围；原检查的拒绝不会被绕过。

调用者必须在提交前以权威数据库读取目标租户、全部领域、目标租户及共享角色和目标租户所有组织，分别执行独立计数，保证无分页截断、无重复、无跨租户记录，并确保目标组织及完整父链存在。构造 `RbacRoleAssignmentSnapshot(tenant, domains, domainCount, roles, roleCount, organizations, organizationCount)` 后调用 `checkRoleAssignmentWithSnapshot(operator, targetUser, finalRoles, snapshot)`。对象和计数仅允许来自可信服务端，不得接收客户端提交的目录或计数。

快照不能自行证明查询完整、计数独立或数据未并发变更。调用事务必须为所有影响授权的角色、组织、租户和领域数据提供适合数据库的隔离或锁，覆盖授权检查直到提交；同时处理并发插入导致的幻读。已有操作人的权限及相关缓存仍遵循宿主的缓存一致性策略，本接口不保证缓存实时刷新；涉及宿主自定义权限字段时也须由调用方保证其一致性。无法满足前提应拒绝分配。

集合长度与计数不符、重复记录、跨租户组织或角色、缺少目标组织或父级、角色缓存的框架安全字段与快照不一致时抛出异常并拒绝。原检查因缓存保守拒绝时，本接口不会放行。旧无快照接口保持原用途。

## 严格签发人视图（开发中）

早期 `checkRoleAssignmentWithSnapshot` 只固定目标目录，并不能固定签发人权限，不能用于依赖签发人权限一致性的生产场景。严格入口使用真实授权 bean 的 `checkRoleAssignmentWithStrictView`：先拒绝快照中的动态脚本，再将权威 `RbacStrictAssignmentView` 绑定到当前线程并隔离领域上下文，在该视图中动态执行真实授权 bean 的原授权入口和后续检查，退出时清理线程上下文。原 baseService 的范围入口若被覆盖则失败关闭。视图要求实际签发人及其租户/共享角色目录、目标用户及目标租户完整组织和角色目录、完整租户与领域目录，并提供独立计数；读取与锁须覆盖相关用户、角色关联、权限及目录直到事务提交，不得使用缓存或客户端内容。

此入口仅接受实现 `RbacStrictAssignmentParticipant` 的可信授权 bean。实现者必须证明所有覆盖的授权钩子、动作目录和匹配规则在整个事务内固定，且不会访问未纳入事务一致性范围的可变外部状态；仅实现标记接口并不能自动保证安全。不能证明时必须拒绝启用。禁止异步和嵌套绑定；动态范围、角色分配前置脚本以及未知或带条件的具体动作均拒绝。通配目标表达式仅在签发人同一有效角色持有可证明覆盖目标的表达式时允许进一步检查：四段普通表达式逐段仅接受签发人段为 `*` 或与目标段完全一致；其余复杂模式仅接受完全相同；调用方必须传入非空同步业务覆盖回调，在该权威视图中以同一个生效角色独立验证操作、租户范围、组织范围、领域范围、字段组和枚举/字典可选值范围对目标的完整覆盖，不得借其他角色的范围并集或残留字段许可补齐，并以可信稳定目录展开当前相关动作。回调只能进一步拒绝，不得使用空回调或从原缓存重新读取身份与角色。包括目标用户类型、角色、表达式或密级条件的动作不在当前可证明范围内。严格入口不从共享缓存读取授权目录。

数据库事务必须防止相关表在提交前发生增删改及幻读，包括共享角色的同码租户覆盖；单独计数与普通行锁无法保证这一点。仅当数据库隔离或所有写入方遵守的事务锁真实覆盖完整目录时才能调用。对 PostgreSQL 使用表锁时须确定统一加锁顺序并在首次读取前加锁；其他数据库不得未经验证仿效。操作人、目录对象及集合必须是可信的独立稳定快照，不得与共享缓存对象共用可变引用。该入口尚未完成生产授权实现及真实端到端验证，不应发布或接入。

受审计实现须在 `checkStrictPermissionCoverage(view, targetRoles)` 中，以每个目标角色为单位寻找同一个有效签发人角色：该角色必须完整覆盖目标角色所有操作表达式与相应字段组、可选值，再调用 `view.checkSingleRoleDataScopeAssignment(view.actor(), view.target(), ownerRole, targetRole, view.targetSnapshot())` 验证该角色自己的租户、组织、领域和密级范围。无法找到满足全部条件的同一角色时抛异常。此方法必须在严格视图绑定期间同步调用，不接受其它服务或客户端角色；它不替代字段权限和可选值检查。普通过期或停用的历史角色码按有效角色解析规则忽略；管理员编码若无有效定义则拒绝，以免触发错误的管理员快捷路径。

严格 participant 须实现 `openStrictAuthorizationCatalog(view)` 并返回非空绑定；它在视图已绑定、任何授权 hook 之前执行。绑定 `close()` 在所有后续成功或异常路径同步执行，之后移除视图。多个 registry 必须依共同锁或一致版本构造目录；逐个拷贝无法证明一致。若打开过程中部分失败，participant 必须在抛错前自行撤销部分绑定。

`verifyFactsUnchanged()` 可在授权期间及业务事务提交前检测已纳入框架指纹的用户、角色、组织、租户和领域字段是否持续变化；非空 `transientExInfo` 或无法冻结的字段值会拒绝。指纹不覆盖未知插件 getter，无法发现一次 hook 内修改后恢复或校验点之后的变化，也无法阻止并发写，因此它不是不可变证明。真实接入必须使用从 JPA 会话和共享缓存独立投影的不可变事实，审计具体 getter/hook，并保持目录锁至提交。

邀请签发阶段若目标用户尚不存在，使用 `RbacStrictIssuerView` 和 `checkInvitationIssuerWithStrictView(view, creationPermission, targetRoleCodes, targetOrgId)`，传入真实签发人、目标租户及完整权威目录，不构造目标用户。participant 必须实现 `openStrictIssuerCatalog` 和 `checkStrictIssuerPermissionCoverage`；如业务指定真实目标组织或新组织父级，必须作为 `targetOrgId` 传入，由入口在隔离的领域上下文中验证归属、有效性和签发人访问范围；组织不适用时可传空，业务须自行确保必填场景不可留空。此入口不验证未来用户或新组织的角色范围，兑换时必须对实际创建的用户和组织执行完整严格分配与单角色范围检查。原数据服务如果自定义了身份、权限、范围、密级或领域计算，默认失败关闭；只有已审计的确切类可直接声明 `RbacStrictBaseParticipant`，不得通过继承授予未知子类信任。目录及对象不可变、事务锁与动作目录一致性前提同上。

兑换后的 `checkRoleAssignmentWithStrictView` 会在绑定的权威视图和独立领域上下文中先执行 `canAdminUser`，拒绝不满足领域、租户、目标用户密级或管理员层级的管理；随后执行角色分配与业务覆盖检查。调用方不应以共享缓存中的另一次检查代替它。对于自定义的原用户管理检查，未经确切实现类审计声明前，严格入口失败关闭。

对于确实不授予后台角色的会员邀请，调用 `checkInvitationIssuerWithoutRoleWithStrictView(view, creationPermission, targetOrgId)`。该入口仍验证创建动作、目标租户和指定组织，并以空角色列表调用签发覆盖 participant。普通有角色入口不接受空角色集合；业务必须保证无角色入口仅用于兑换时也不会授予后台角色的邀请类型。

渠道类签发使用带 `RbacStrictIssuerVeto` 的重载。真实 participant 必须通过 `supportsStrictIssuerVeto` 精确认可已审计的提供方；未知提供方拒绝。附加检查在创建动作、租户、组织、角色及 participant 覆盖均通过后，于同一个严格视图、受控目录和隔离领域上下文中同步执行，只能进一步拒绝。渠道分支必须传入提供方，且其候选和字段值来源必须受同事务稳定性保护；无附加检查的重载只用于业务上不需要该校验的分支。

业务需要解析目标租户角色时，使用严格 view 的 `resolveTargetRoles(codes)`。它沿用有效租户同码优先、否则回退有效公共定义的规则，未知编码、目录重复或事实发生变更会拒绝；无需在业务代码复制解析器。外部邀请禁止租户覆盖的额外业务限制仍须单独校验。

平台用户在严格视图中按某一租户查询可访问组织时，使用 `loadUserAccessibleOrgListForTenant(realActor, tenantId, true)`。该方法保留真实平台身份并按正常范围、领域和密级过滤，仅访问指定租户组织；未授权租户不返回组织，已授权但视图未覆盖的租户目录失败关闭。既有无租户参数的入口及其宿主覆盖语义保持不变。

需要执行已审计 DAO 条件时，调用 `ExpressionUtils.withRestrictedVariableResolvers(List.of(), () -> { /* 同步受控查询 */ return result; })`。线程解析器在退出时恢复，嵌套和作用域内改写被拒绝；不传播到其它线程。启用配套 Simple DAO 版本后，自动全局/线程变量和 BeanFactoryResolver 被隔离，内置 `isEmpty`、`isNotEmpty` 不受变量覆盖。该机制不禁用 SpEL 的所有语言能力，不能执行不可信表达式。
